# ADR-050: v0.2 installation component ownership

- Status: **Accepted — v0.2 target architecture; implementation deferred**
- Date: 2026-09-27
- Decision owners: Product, Desktop, Platform / Distribution, Database, Release, Security, UX / Accessibility

## Context

[ADR-049](ADR-049-v0.2-effortless-installation-architecture.md) fixes the
ordinary product journey and installer/first-run split. The existing accepted
ADRs separately define package lifecycle, migration safety, SecretStore,
user-level startup, local IPC and independent GUI/client lifecycles. P004 and
the implementation prompts need a single ownership and effect contract that
connects these decisions without moving authority or promising global rollback.

## Decision

1. The Installation Coordinator owns common lifecycle policy: inspect,
   preflight, plan, request scoped effects, verify, classify, reconcile and
   report. Platform adapters own only their created or explicitly authorized
   integration; native package managers retain package transaction authority.
2. Every mutation is an identified, owned effect with preconditions, privilege,
   verification, retry/reconciliation, reversibility and preservation rules.
   Compensation is effect-specific. `OutcomeUnknown` requires authoritative
   reconciliation before retry; no blind replay or global rollback promise.
3. Package payload, platform integration, application config, credentials,
   client sync state, user libraries, server config/database/object data,
   external dependencies and ephemeral state have distinct canonical owners.
   Repair touches package payload and owned integration only. Ordinary
   uninstall preserves durable user and server state. Destructive purge is a
   separate explicit operation with exact validated scope.
4. Installer completion means verified desktop/client installation and
   required integration. First-run starts afterward as the user. Connect and
   Host are first-run choices; Host transfers to a separate Server Bootstrap
   Coordinator. Neither coordinator owns synchronization; `synveil-client`
   does.
5. Prefer per-user Windows installation and user-level AppImage use. DEB/RPM
   transactions use visible native package-manager authorization. Platform
   startup is opt-in and owned by its adapter; Linux package hooks remain
   non-starting. No implementation technology or managed PostgreSQL
   distribution is selected by this ADR.
6. Preserve the established invariants: ROOT UNAVAILABLE is not deletion
   authority; non-empty folders are not deletion sets; unknown/future database
   schema fails closed; SecretStore owns durable credentials; desktop/client
   control remains user-scoped local IPC; durable sync mutation precedes its
   runtime signal; GUI and synchronization lifecycles remain independent.

The normative architecture, resource matrix, lifecycle model and blocker
disposition are in [INSTALLATION_ARCHITECTURE.md](../v0.2/INSTALLATION_ARCHITECTURE.md).
This ADR refines ADR-049 and supplements ADR-021, ADR-024, ADR-037–043 and
ADR-046; it does not supersede them or accept proposed ADR-019/020.

## Consequences

P004 can express acceptance at the installation completion boundary without
conflating first-run, Host readiness or synchronization. Later engines and
adapters must preserve native package authority and inspect/reconcile uncertain
effects. Repair and uninstall remain data-preserving; purge requires separate
scope and consent. Host provisioning decisions remain gated by their named
roadmap/ADR owners.

## Alternatives considered

- Put server provisioning and credentials inside the ordinary installer:
  rejected because Connect users would acquire deployment scope and privilege.
- Let the installer repair application, client and server state together:
  rejected because it violates canonical data owners and migration safeguards.
- Promise whole-transaction rollback for every package and OS effect: rejected
  because external/native effects may be irreversible or uncertain.
- Make package hooks start or enable the persistent client: rejected because
  user consent and supervisor ownership remain explicit.

## Migration and review trigger

No implementation, schema, migration, artifact, dependency, version or tag is
created by this decision. Product version remains `0.1.0`, server migration
count remains 36, client migration count remains 7 and
`LOCAL_SCHEMA_VERSION = 7`. P004 must preserve these ownership boundaries.
Changes to destructive scope, credentials, privilege, startup, database
authority, service model or public reachability require review by the named
owner and an ADR update or superseding decision.

## Bối cảnh

[ADR-049](ADR-049-v0.2-effortless-installation-architecture.md) chốt hành
trình sản phẩm thường và ranh giới installer/first-run. Các ADR Accepted hiện
có quy định riêng về vòng đời package, an toàn migration, SecretStore, startup
cấp user, IPC cục bộ và lifecycle độc lập của GUI/client. P004 và các prompt
triển khai cần một hợp đồng ownership/effect thống nhất để kết nối các quyết
định này mà không chuyển quyền sở hữu hoặc hứa rollback toàn cục.

## Quyết định

1. Installation Coordinator sở hữu policy lifecycle chung: kiểm tra,
   preflight, lập plan, yêu cầu effect có scope, verify, phân loại,
   reconcile và báo kết quả. Adapter platform chỉ sở hữu integration do nó
   tạo hoặc được ủy quyền rõ; package manager native giữ quyền giao dịch
   package.
2. Mỗi mutation là một effect có identity, owner, precondition, privilege,
   verification, quy tắc retry/reconciliation, mức độ đảo ngược và ràng buộc
   bảo toàn. Compensation được xét theo từng effect. `OutcomeUnknown` phải
   reconcile với state authoritative trước khi retry; không blind replay và
   không hứa rollback toàn cục.
3. Payload package, platform integration, application config, credential,
   client sync state, library của user, server config/database/object data,
   external dependency và ephemeral state có owner canonical riêng. Repair chỉ
   chạm package payload và integration sở hữu. Uninstall thường giữ durable
   state của user/server. Destructive purge là thao tác riêng, xác nhận tường
   minh và có scope được kiểm tra chính xác.
4. Hoàn tất installer nghĩa là desktop/client đã cài và integration cần thiết
   đã verify. First-run bắt đầu sau đó, dưới quyền user. Host hoặc Connect là
   lựa chọn first-run; Host chuyển sang Server Bootstrap Coordinator riêng.
   Không coordinator nào sở hữu synchronization; `synveil-client` sở hữu.
5. Ưu tiên Windows per-user và AppImage cấp user. DEB/RPM dùng authorization
   hiển thị của package manager native. Startup platform là opt-in và thuộc
   adapter; hook Linux không tự start. ADR này không chọn technology triển
   khai hoặc distribution PostgreSQL managed.
6. Giữ invariant hiện có: ROOT UNAVAILABLE không phải quyền xóa; folder không
   rỗng không phải deletion set; schema database unknown/future fail closed;
   SecretStore sở hữu credential bền vững; control desktop/client là IPC cục
   bộ theo user; durable sync mutation đứng trước runtime signal; lifecycle
   GUI và synchronization độc lập. Durable mutation đứng trước runtime
   signal/wake; signal mất hoặc coalesce không rollback dữ liệu durable.

Architecture normative, ownership matrix, lifecycle và blocker mapping nằm ở
[INSTALLATION_ARCHITECTURE.md](../v0.2/INSTALLATION_ARCHITECTURE.md). ADR này
refine ADR-049 và bổ sung ADR-021, ADR-024, ADR-037–043, ADR-046; không thay thế
chúng và không chấp thuận ADR-019/020 đang Proposed.

## Hệ quả

P004 có thể viết acceptance tại ranh giới hoàn tất cài đặt mà không gộp
first-run, Host readiness hay synchronization. Engine và adapter sau này phải
giữ native package authority và inspect/reconcile effect chưa rõ. Repair và
uninstall bảo toàn dữ liệu; purge cần scope và consent riêng. Quyết định Host
vẫn chờ các owner ADR/roadmap đã nêu.

## Phương án được xem xét

- Đưa provisioning server và credential vào installer thường: bác bỏ vì user
  Connect sẽ bị kéo vào deployment và privilege không cần thiết.
- Cho installer repair chung application, client và server state: bác bỏ vì
  vi phạm owner dữ liệu canonical và safeguard migration.
- Hứa rollback toàn giao dịch cho mọi package/OS effect: bác bỏ vì effect
  native/bên ngoài có thể không đảo ngược hoặc có kết quả chưa rõ.
- Để package hook start hoặc enable client persistent: bác bỏ vì consent của
  user và ownership supervisor phải tường minh.

## Migration và điều kiện xem xét lại

Quyết định này không tạo implementation, schema, migration, artifact,
dependency, version hoặc tag. Product version giữ `0.1.0`, server migration
giữ 36, client migration giữ 7 và `LOCAL_SCHEMA_VERSION = 7`. P004 phải giữ
ownership boundaries này. Thay đổi destructive scope, credential, privilege,
startup, database authority, service model hoặc public reachability cần owner
review và cập nhật ADR hoặc quyết định superseding.
