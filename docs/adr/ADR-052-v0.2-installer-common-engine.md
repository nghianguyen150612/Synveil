# ADR-052: v0.2 installer common engine and platform adapter boundary

- Status: **Accepted**
- Date: 2026-09-28
- Decision owners: Distribution, Platform, Security, Desktop

## Context

Windows Setup, native Linux packages, AppImage integration, quick install, and
later repair coordinators need the lifecycle and effect safety rules from
ADR-050 without duplicating policy. OS mechanics, acquisition, persistence,
product lifecycle policy, and user-facing errors have different owners.

## Decision

Implement the coordinator as the platform-neutral Rust workspace crate
`synveil-install-engine`. Rust gives later native front ends one typed,
serializable contract while keeping ordering, plan validation, ownership,
precondition rechecks, effect verification, result classification,
reconciliation, and bounded compensation in one place. Platform adapters
implement only typed inspection and mechanics; the API has no command-string,
network, database, SecretStore, synchronization, UI, or server-bootstrap hook.

The closed lifecycle is `Preflight → Plan → Install → Integrate → Verify →
Complete`. Preflight and planning are read-only. Every mutation is declarative,
owned, rechecked immediately before apply, and verified. `OutcomeUnknown` is
reconciled by stable effect identity and is never blindly replayed. Complete
requires final installer-owned verification and means only launch eligibility,
not first-run, synchronization, or server readiness.

Prompt007 execution is in memory and emits deterministic events. It creates no
journal or reboot-resume facility: P008 owns durable journaling. P009 owns the
detailed upgrade, repair, uninstall, and any separately authorized purge
semantics. P010 owns final user-facing error mapping. P006 owns release
acquisition and publisher trust and hands over typed verified-artifact evidence.
P012+ and P021+ own native Linux and Windows mechanics. Server bootstrap stays
separate, and synchronization remains owned by `synveil-client`.

## Consequences

Adapters can be tested exhaustively without changing the host. A deterministic
plan and event stream can later be journaled without changing lifecycle policy.
Native package authorities retain their databases and transactions; forbidden
durable resource owners cannot reach adapter mutation through this engine.

## Alternatives considered

- Separate lifecycle implementations per platform were rejected because safety
  policy would drift.
- A generic shell-command effect was rejected because it bypasses ownership.
- Persistence in the engine was rejected because P008 must define durable and
  interruption semantics explicitly.
- Full upgrade/uninstall policy and polished errors were deferred to P009/P010.

## Migration and review trigger

The engine contract begins at schema version 1. Product version and database
schemas do not change. Review this ADR before expanding mutation ownership,
adding persistent state, or allowing a platform adapter to execute untyped
commands. Future schema versions must fail closed until explicitly supported.
