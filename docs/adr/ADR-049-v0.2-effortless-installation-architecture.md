# ADR-049: v0.2 effortless installation architecture / Kiến trúc cài đặt dễ dàng v0.2

- Status / Trạng thái: **Accepted / Chấp thuận — v0.2 target contract / contract mục tiêu v0.2**
- Date / Ngày: 2026-09-27
- Decision owners / Chủ sở hữu quyết định: Product, Desktop, Platform / Distribution, Database, Release, Security, UX / Accessibility

## Context (English)

The released v0.1.0 source is
`fa23232ff0154f627ebdd221ec5435134f177af0`. It has Linux DEB/RPM packaging,
a Windows portable ZIP, two independent desktop/client processes and guarded
persistent-state migrations. These foundations do not yet establish a
no-terminal clean-machine installation and managed self-hosting journey.

The v0.2 goal is download → install → launch → guided setup → first library →
synchronization, using sensible defaults and product language. Installer-side
database/service/account questions would make every Connect user perform
deployment planning, often in an elevated process. Mixing package repair and
user-state repair would also threaten the existing data-preservation boundary.

## Decision (English)

1. **Install the desktop/client product; select Host or Connect in first-run.**
   The ordinary installer does not provision a server or collect credentials.
   First-run runs as the user and offers **Host Synveil on this device** and
   **Connect to an existing Synveil server**. Host choice may acquire additional
   verified components through its own resumable coordinator; Connect must not
   require a server/database download. Existing profiles bypass fresh setup.
2. **Primary distribution is native and explicit.** Windows x86_64 targets
   `SynveilSetup.exe`, Debian/Ubuntu x86_64 DEB, qualified Fedora/RPM x86_64 RPM,
   and qualified generic Linux x86_64 AppImage. ZIP may remain an advanced
   Windows alternate; a verified Linux install script is an alternate terminal
   path. Exact OS/runtime qualification is required before support claims.
   Other architectures and Apple/mobile are outside this installation matrix.
3. **Use a common conceptual plan/result contract with native adapters.**
   `Preflight → Plan → Acquire → Verify → Install → Integrate → VerifyInstallation
   → Complete`; finite failures, authenticated payloads, bounded redacted
   diagnostics, owned effects and durable interruption evidence. Reconcile an
   unknown outcome before any repeated mutation. Native package managers and
   the existing manifest/lifecycle layer remain authoritative; no custom package
   manager or new runtime API is introduced by this ADR.
4. **Separate ownership and completion gates.** Installation success validates
   required binaries/runtime/integration, then Finish may open the desktop.
   Host readiness and first synchronization are separate results. Repair/update
   replaces package-owned payload/integration and preserves configuration,
   credentials, databases, profiles, sync state, libraries and server objects.
   Ordinary uninstall preserves those classes. Permanent data removal requires
   a separately named, explicit destructive choice with exact scope; existing
   administrative purge never expands into external library/object/backup or
   PostgreSQL deletion.
5. **Use least privilege and explicit user choices.** Prefer Windows per-user
   installation without admin. Linux package-manager elevation is visible;
   AppImage normally remains user-level. Product copy says **Start Synveil when
   I sign in**; enabling requires an explicit user action and saved disable
   choices survive repair/update. Linux package hooks remain non-starting.
   ADR-041's user-level supervision, writer arbitration and independence of
   GUI/client lifecycles remain unchanged. Host services have a separate plan.
6. **Define guided hosting without selecting its infrastructure implementation.**
   Ask for file storage, automatic start and device reach. Keep PostgreSQL as
   server authority and use a future managed adapter outside core; external
   database/bind/origin/TLS/service controls are progressively disclosed Advanced
   options. Accept/supersede proposed ADR-019 and close `OD-PLAT-001` before
   provisioning code; close the host portion of `OD-PLAT-002` before service
   implementation. New access mechanisms need ADR-020/`OD-PLAT-003` resolution.
   Local/private bootstrap precedes explicit access choices; no silent public
   exposure or mandatory proprietary relay is selected.
7. **Require recoverable, data-preserving lifecycle evidence.** Interrupted
   acquisition, replacement, integration and bootstrap must safely resume or
   offer Repair without false success. Preserve ADR-021/024 and Prompt115
   migration checks, verified backups, schema-compatible rollback/restore limits
   and unknown-state rejection. Do not infer transactional package rollback from
   atomic file replacement.

The detailed normative [product contract](../v0.2/INSTALLATION_PRODUCT_CONTRACT.md)
and [roadmap](../v0.2/ROADMAP.md) define the primary flows and acceptance IDs.
This ADR supplements accepted lifecycle/desktop ADRs; it does not supersede
their ownership or released-data compatibility, change v0.1 packaging behavior,
or accept the still-proposed ADR-019/020 implementations. It resolves the v0.2
installer/first-run boundary; the host supervisor and database distribution
remain open as stated above.

## Consequences (English)

The installer stays small in product decisions and can use native package
conventions. First-run owns resumable host setup and can explain remaining
connectivity work. Connect users avoid unnecessary infrastructure. Shared
verification/ownership policy constrains each platform adapter without moving
platform machinery into the domain core. A per-user host may depend on sign-in;
an always-on host needs a separately reviewed service/privilege design.

The managed-host path cannot be promoted while its decisions or native evidence
are missing. Approximately five minutes is a usability target under available
server/connectivity conditions, not a benchmark guarantee. All advertised
platforms need native clean-machine, repair/update/uninstall and interruption
evidence; fixtures and cross-builds retain narrower claims.

## Alternatives (English)

- Server/database setup inside every installer: rejected because it couples
  package installation, credentials and elevated deployment work for all users.
- Separate mandatory client/server installers at the first download choice:
  rejected as the ordinary product path because users must choose architecture
  before learning Host versus Connect; advanced administration remains possible.
- ZIP/terminal instructions as the primary desktop path: rejected because they
  fail the no-terminal/native-convention release bar.
- Reset/delete state to repair an application, or silently replay uncertain
  bootstrap: rejected because they violate canonical ownership and recovery.
- Select bundled PostgreSQL, a privileged host service or a relay by implication:
  deferred until their own reviewed decision and evidence gates.

## Migration and review trigger (English)

Prompt001 changes documentation only: version `0.1.0`, 36 server migrations,
7 client migrations and `LOCAL_SCHEMA_VERSION = 7` remain frozen. No artifact,
runtime, dependency, schema, tag or release is created. Before implementation,
close the decisions named in the roadmap and validate all affected accepted
contracts. A future change to ownership, data removal, privilege, supervisor,
server database or public exposure requires an explicit ADR review; released
state compatibility cannot be weakened by UX convenience.

Before v0.2 promotion, pass INSTALL-JOURNEY-1 through INSTALL-JOURNEY-8 and
FIRST-RUN-1/2 for applicable qualified targets, supported-source upgrades and
coordinated restore. Ordinary installation must be completable through UI
alone. No successful documentation gate substitutes for native delivery.

## Bối cảnh (Tiếng Việt)

Source phát hành v0.1.0 là
`fa23232ff0154f627ebdd221ec5435134f177af0`, có package DEB/RPM Linux, ZIP
portable Windows, hai process desktop/client độc lập và migration bảo vệ state.
Các nền tảng này chưa chứng minh journey cài đặt trên máy sạch không terminal
hay self-hosting được quản lý. Mục tiêu v0.2 là tải → cài → mở → setup có hướng
dẫn → library đầu tiên → đồng bộ, dùng mặc định hợp lý và ngôn ngữ sản phẩm.
Đưa câu hỏi database/service/account vào installer buộc cả người dùng Connect
phải lập kế hoạch deployment, thường trong process elevated. Trộn repair package
với repair state người dùng có thể phá ranh giới bảo toàn dữ liệu.

## Quyết định (Tiếng Việt)

1. **Installer cài desktop/client; first-run chọn Host hoặc Connect.** Installer
   thường không provision server hay nhận credential. First-run chạy với user,
   cho chọn **Host Synveil on this device** hoặc **Connect to an existing Synveil
   server**. Host có thể tải component đã verify qua coordinator có khả năng
   tiếp tục; Connect không bắt tải server/database. Profile đã có không phải
   chạy setup mới sau repair/update.
2. **Artifact chính theo nền tảng và được nêu rõ.** Windows x86_64 dùng
   `SynveilSetup.exe`, Debian/Ubuntu x86_64 dùng DEB, Fedora/RPM x86_64 đã được
   kiểm chứng dùng RPM, generic Linux x86_64 trong baseline đã kiểm chứng dùng
   AppImage. ZIP Windows chỉ là lựa chọn Advanced; script Linux đã verify là
   đường terminal thay thế. Phải xác định OS/runtime cụ thể trước claim hỗ trợ.
   Kiến trúc khác và Apple/mobile nằm ngoài matrix cài đặt này.
3. **Dùng contract plan/result khái niệm chung với adapter native.**
   `Preflight → Plan → Acquire → Verify → Install → Integrate → VerifyInstallation
   → Complete`; lỗi hữu hạn, payload xác thực, diagnostic bounded/redacted,
   effect có ownership và bằng chứng interruption durable. Outcome chưa rõ phải
   reconcile trước mutation lặp lại. Package manager native và manifest/lifecycle
   hiện có vẫn là authority; ADR không tạo package manager riêng hay runtime API.
4. **Tách ownership và gate hoàn tất.** Thành công cài đặt phải verify binary,
   runtime và integration cần thiết rồi Finish mới có thể mở desktop. Readiness
   Host và đồng bộ đầu tiên là result riêng. Repair/update thay payload/
   integration của package và giữ config, credential, database, profile, sync
   state, library và object server. Uninstall thường giữ các lớp đó. Xóa dữ liệu
   vĩnh viễn là quyết định destructive riêng, có tên/phạm vi rõ và xác nhận
   tường minh; purge quản trị hiện có không được mở rộng để xóa library/object/
   backup bên ngoài hoặc PostgreSQL.
5. **Least privilege và lựa chọn user tường minh.** Ưu tiên install Windows
   per-user không admin. Elevation package manager Linux phải hiển thị; AppImage
   thường user-level. Copy nói **Start Synveil when I sign in**; enable cần user
   action rõ, repair/update giữ lựa chọn disable. Hook package Linux vẫn không
   tự start. Giữ supervision user-level, writer arbitration và lifecycle GUI/
   client độc lập theo ADR-041. Service Host có plan riêng.
6. **Định nghĩa hosting có hướng dẫn mà chưa chọn implementation hạ tầng.**
   Hỏi nơi lưu file, tự khởi động và cách thiết bị khác kết nối. PostgreSQL vẫn
   là authority server; adapter managed tương lai nằm ngoài core. Database ngoài,
   bind/origin/TLS/service chỉ hiện khi mở Advanced. Chấp thuận/thay thế ADR-019
   Proposed và đóng `OD-PLAT-001` trước code provisioning; đóng phần Host của
   `OD-PLAT-002` trước code service. Cơ chế access mới cần giải quyết ADR-020/
   `OD-PLAT-003`. Bootstrap local/private trước lựa chọn access tường minh;
   không tự expose public hay chọn relay độc quyền bắt buộc.
7. **Lifecycle phải phục hồi được và bảo toàn dữ liệu.** Download, thay file,
   integration và bootstrap bị gián đoạn phải tiếp tục an toàn hoặc cho Repair,
   không báo thành công giả. Giữ ADR-021/024 và guard migration Prompt115,
   backup đã verify, giới hạn rollback/restore tương thích schema, reject state
   không rõ. Atomic replacement từng file không chứng minh rollback toàn package.

[Product contract](../v0.2/INSTALLATION_PRODUCT_CONTRACT.md) và
[roadmap](../v0.2/ROADMAP.md) quy định flow và ID acceptance chi tiết. ADR này
bổ sung ADR lifecycle/desktop đã Accepted; không thay ownership hay compatibility
của dữ liệu đã phát hành, không đổi behavior package v0.1, không chấp thuận
implementation ADR-019/020 còn Proposed. Ranh giới installer/first-run v0.2 được
chốt; supervisor Host và distribution database vẫn mở như trên.

## Hệ quả (Tiếng Việt)

Installer ít quyết định sản phẩm và theo quy ước package native. First-run quản
lý setup Host có thể tiếp tục, giải thích connectivity còn thiếu; Connect không
phải dựng hạ tầng. Policy verification/ownership chung ràng buộc adapter mà
không đưa machinery platform vào domain core. Host per-user có thể phụ thuộc
sign-in; Host luôn chạy cần thiết kế service/privilege được review riêng.

Không promote managed Host khi decision hoặc bằng chứng native còn thiếu.
Khoảng năm phút là mục tiêu usability khi server/connectivity đã có, không phải
cam kết benchmark. Mọi platform quảng bá cần bằng chứng native máy sạch, repair/
update/uninstall và interruption; fixture/cross-build chỉ chứng minh phạm vi hẹp.

## Phương án khác (Tiếng Việt)

- Setup server/database trong mọi installer: loại vì trộn cài package,
  credential và deployment elevated cho mọi user.
- Bắt chọn installer client/server riêng ngay khi tải: loại cho đường thường
  vì user phải chọn kiến trúc trước khi hiểu Host/Connect; quản trị Advanced vẫn có.
- ZIP/hướng dẫn terminal là đường desktop chính: loại vì không đạt gate
  không terminal và quy ước native.
- Reset/xóa state để repair app hoặc lặp bootstrap outcome chưa rõ: loại vì
  vi phạm ownership và recovery canonical.
- Ngầm chọn bundle PostgreSQL, service Host privileged hay relay: hoãn cho
  decision và gate bằng chứng được review riêng.

## Điều kiện di chuyển và xem xét lại (Tiếng Việt)

Prompt001 chỉ đổi tài liệu: giữ version `0.1.0`, 36 migration server,
7 migration client và `LOCAL_SCHEMA_VERSION = 7`. Không tạo artifact, runtime,
dependency, schema, tag hay release. Trước implementation phải đóng decision
trong roadmap và validate contract Accepted liên quan. Đổi ownership, xóa dữ
liệu, privilege, supervisor, database server hoặc public exposure cần review ADR
tường minh; sự thuận tiện UX không được làm yếu compatibility state đã phát hành.

Trước promote v0.2, pass INSTALL-JOURNEY-1 đến INSTALL-JOURNEY-8 và FIRST-RUN-1/2
trên target tương ứng đã kiểm chứng, upgrade từ version được hỗ trợ và restore
phối hợp. Cài đặt thường phải hoàn tất bằng UI; gate tài liệu thành công không
thay thế delivery native.
