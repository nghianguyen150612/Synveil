# ADR-062: v0.2 Managed Server Storage Location

Status / Trạng thái: **Accepted / Chấp thuận**
Date / Ngày: 2026-10-04
Decision owners / Chủ sở hữu quyết định: Synveil v0.2 architecture

## Context / Bối cảnh

P031 provides a typed managed server configuration and deliberately leaves
storage selection to P032. The repository already has a canonical
`LocalFilesystemObjectStore` with its own marker, layout validation, staging,
integrity, durability behavior, and capability model. The product needs a
recoverable managed-server ownership layer without confusing opaque server
objects with user-visible synchronized files.

## Decision / Quyết định

1. `SERVER_OBJECT_DATA` and `CLIENT_LIBRARY` are separate product concepts,
paths, and ownership boundaries. The user-facing question is “Where should
   Synveil store server data?”
2. The recommended Linux Personal/Home root is
   `/var/lib/synveil/storage`. A selection must be a dedicated root. Selecting
   a mount root proposes a dedicated `Synveil` child.
3. Setup first inspects without persistent mutation, then requires explicit
   confirmation and binds a review plan to configuration and filesystem
   identity. Only an exact safe new leaf or existing empty directory may be
   initialized.
4. P031 V1 storage state is `NotConfigured`, `PreparingLocal`, or
   `ConfiguredLocal`. `PreparingLocal` durably preserves the chosen root,
   UUIDv7 storage identity, and selected-parent/root filesystem identity before
   initialization. `ConfiguredLocal` also preserves the validated
   LocalFilesystemObjectStore capability report so runtime can reopen without
   reprobeing or mutating storage. It is written only after storage is ready
   and verified.
5. A bounded strict `.synveil-server-storage.json` marker binds both the
   server installation ID and storage ID to backend and object-layout version.
   The existing `.synveil-storage-root` remains exclusively owned by the
   LocalFilesystemObjectStore. Both identities must match configuration;
   path alone is never authority.
6. Non-empty unknown directories, malformed/future markers, foreign managed
   storage, and legacy ObjectStore roots without the server marker fail closed.
   There is no automatic adoption or destructive cleanup.
7. Managed API and worker runtime open existing storage only. A missing,
   redirected, replaced, or mismatched configured root remains unavailable and
   is never recreated or replaced automatically.
8. P032 does not implement ordinary relocation. A configured root can be
   reselected only for idempotent verification; another root requires a future
   coordinated migration design.
9. Managed local filesystem execution is initially Linux-qualified. Capacity
   comes from native filesystem APIs, write/durability is probed after
   confirmation, and optional filesystem accelerators are not correctness
   requirements. The existing upload boundary does require the adapter's
   tested atomic-promotion behavior; the current local adapter uses a
   same-root hard link and has no portable promotion fallback.

## Consequences / Hệ quả

The setup can resume the same operation after interruption without generating
a new root or identity. Unknown user data is preserved. Runtime cannot turn a
missing mount into empty replacement storage. P033 must provide safe parent
ownership and service handoff; P034–P036 remain separate owners. The selected
root contains only server object data, not PostgreSQL, config, credentials, or
client-library files.

## Alternatives / Phương án khác

- Treat a path string or `.synveil-storage-root` as server ownership: rejected
  because either can refer to copied, legacy, replaced, or unrelated storage.
- Auto-adopt non-empty or legacy roots: rejected because content ownership is
  ambiguous.
- Initialize from API/worker startup: rejected because runtime must never create
  a replacement for missing configured storage.
- Allow ordinary path edits: rejected because safe relocation requires
  database/object coordination and rollback.

## Migration and review trigger / Điều kiện di chuyển và xem xét lại

Any future storage backend, cross-platform managed adapter, marker schema
change, service ownership model, or object migration must preserve the two
identity checks, resumable durable intent, fail-closed unknown-data handling,
and existing-only managed runtime boundary. Such a change requires a new ADR or
an explicitly superseding decision.
